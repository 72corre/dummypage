# 塔ツール（アプリ本体）— 土台＋M1＋核のループ＋残りの ME 非依存画面 スライス

作成: 2026-11-18（第3スライス同日追記）。位置づけ: requirements.md v3 / ui-flow.md v3 / tech-foundation.md に基づく実装。第1スライスは土台（PWA・保存・状態導出）と M1 マップ画面。第2スライスは核のループ: マスのシート（M3）、編成を選ぶ（M5）、開始前の確認表示（M8）、戦いの後の結果操作（M10）、回復の境界確認（M9 のUI）、探索（M7）。第3スライスは残りの ME 非依存の画面と横断機能: 記録画面（M10 の振り返り・H1 の戦績・H3 の月の締め）、メギド画面（所持・育成の入力）、ズレの修正（H2）、ラン途中からの開始（H3）、塔効果バフの保持と表示。

## 動かし方

- ビルド工程はない。`build/app/` を静的サーバのルートとして配信すると、`index.html` が入口になる（データは `./data/` の生成物を読む。2026-11-27 の平置き化で、データは `build/app/data/` に寄せた）。
- 検証: `node tests/run-tests.mjs`（アサーション777件）。実ブラウザ検証は `/tmp/pwtest/verify.mjs`（50項目）、`/tmp/pwtest/verify-feel.mjs`（45項目、操作感の仕上げ便）、`/tmp/pwtest/verify-counter.mjs`（36項目、索引・対策・需要の実装便）。合計131項目。

## 第1スライスで決めた導出の意味論

- ランの初期状態（操作が無い場合）: 1F・塔破力30・スタートマス処理済み・全員 絶好調。`startRun` 操作で任意の階から初期化し直せる（H3 の土台）。
- 戦闘コスト: 1（ボスの初回だけ0。2回目からは1）。勝利 −1段階、敗北 −2段階、リタイアはコンディション不変（ゲームの実挙動）。
- 探索コスト: 1、参加者 −2段階。塔破力マスは箱の実量で回復（操作に `powerGain` があればそれを優先）。
- 回復の自動反映（M9）: 対象スタイルで絶好調より悪い者を悪い順に取る。探索に送った本人は対象外。同段階グループを途中で割る場合は境界として返し、操作の `boundaryPicks` が揃うまでは `recoveryPending` として残す（自動分は先に適用する）。
- 見通し（M1）: 踏破した階が3つ未満なら判定を出さず事実のみ（現在値、次の塔破力マスの階、「最短路上に塔破力マスは無い」）。3つ以上でペース方式（踏破した階の消費合計÷階数、×1.15 の余裕、回復の先読みは塔破力マスの回収実績がある場合だけ期待度3・赤の実量）。research/tower-power-verification.md の確定条件どおり。
- 見通しの帯は「今いる階（導出された現在階）」に固定し、階の注記（31F 等）だけが閲覧中の階に追随する。
- 所持の意味論: `megidoDetails` が未設定（null）なら全員所持として扱う（初回の方式）。移行や入力でオブジェクトが入った後は `owned === true` の明示がある者だけが所持（旧ツールの意味論）。

## 第2スライスで決めた意味論

- 歩数（判断を含まない操作）: 戦闘フローは4タップ（マス→編成を選ぶ→編成の行→結果）。選び直しは +2（シートを閉じずに一覧を重ねる）。探索は3タップ（マス→「探索の結果を付ける」→箱色）。ui-flow.md の設計値どおりで、テストで照合している。
- 箱色の付け方: 探索の下部バーのボタンでシート内に箱色4ボタンを出し、タップで確定する（ui-flow.md の確定仕様。ボタン自体が4色に分かれる形ではない）。
- ランダム回復マスは、箱色の後に「実際に回復したスタイル」を確認してから確定する（ゲームの結果画面で分かる事実の入力。導出側の `style` が実結果を要求するため）。固定スタイルの回復マスは箱色タップで即確定する。
- 回復マスは確定後もシートを開いたままにし、M9 の内訳（自動で回復した相手、境界の選択肢）をその場で出す。境界の選択が揃うと探索の操作へ `boundaryPicks` を書き足して履歴を作り直す。
- 敗北・リタイアは操作を即時に積み、シート内に結果後の材料（そのマスの過去の結果、コスト差、次に使える編成があるか）を残す。勝利は即座にシートを閉じる。断定的な敗因は出さない。
- 探索の組み合わせ（M7）: 探索力 ＝（攻撃力×素早さ/1000 ＋ HP×防御力/10000）×（1＋奥義Lv×0.05）×コンディション補正。奥義Lvは利用者の育成値（無ければ既定3）。気絶は候補外、同一キャラクター（`no`）は重ねない。人数が最小で、合計が推奨×1.4 以上になる最小の組み合わせを答えとして出す。届かない場合は最善の組み合わせと到達できる期待度を正直に出す。
- おすすめ補正（1.8倍）は掛けない。おすすめクラス・スタイルは挑戦ごとに変わり、構造データに無いため。シートにその旨を注記する。
- 編成の使える／使えない（M5）: 導出で判定できる理由だけを使う（メンバーがいない、基礎データに無い、未所持、気絶）。理由は常時表示し、使えない行をタップしても選択されず理由が強調される。並びは「使える編成→最悪段階の軽い順→名前順」（対応範囲の順位づけは手段の索引の生成後）。
- 確認表示（M8）: 5枠を位置どおり（中央がリーダー）に並べ、枠ごとにオーブ名（空きは「オーブなし」と明記）。確認タップは置かない。ME の要約はデータが無い間は出さない。
- オーブマスタ: M8 のオーブ名表示のため、生成パイプラインに `orbs.v1.json`（606件、旧ツールのマスタ `research/orbs.json` が正本。移行した orbId と同じキー空間）を追加した。検証項目24として整合性チェックが入っている。

## 第3スライスで決めた意味論

- 記録画面（M10 の振り返り・H1）: 今のランはマスごとの結果を階ごとに並べる。敵ごとの苦手傾向と編成ごとの勝率は、同じ相手・同じ編成で3戦以上した行だけを出す（`TENDENCY_MIN_BATTLES` / `FORMATION_RATE_MIN_BATTLES` = 3）。届かない間は「現在の最大件数」を添えて出さない旨を明示する。集計は今のランと過去のアーカイブの全ランの操作履歴から導出する。
- 月の締め（H3）: 記録画面の操作で、今のランの操作履歴をアーカイブ（年月ラベル、階ごとの要約文、戦績の統計）として records に保存し、履歴を空にして新しいランを始める。月替わりは `meta.runMonth` で検出し、起動時に前月のランが残っていれば「閉じる／続ける」を1枚で出す。月の締めの後と、途中開始・読み込みの後は runMonth を今月に合わせる。
- 階ごとの要約文（アーカイブ）: 「○マス処理、ボスは「編成名」編成で勝利」の形。マスのシートの「前回」の手渡しは、直近のアーカイブの要約も対象にする（年月つきで出す）。
- ズレの修正（H2）: 結果の付け直しは、そのマスのシートの「結果を直す」から行い、履歴の中の最後の該当操作を書き換えて導出し直す（記録画面の「ズレの直し」には対象マスの一覧と導線を出す）。能力上昇マスの付け直しは複合結果のため対象外とし、元に戻す→付け直しの手順を案内する。コンディションの直しは新しい操作 `conditionFix`（段階を直接置く）で表し、緊急回復も同じ経路。報告漏れの検出（`validateOps`）は履歴を再演し、処理済みへの重ね付け／解放されていないマスへの結果／塔破力が足りない状態での結果／塔破力のマイナスを「疑い」として、帯に1行（タップで記録画面）と記録画面に明細を出す。検出は提示までで、自動修正はしない。
- ラン途中からの開始（H3）: 開始する階、現在の塔破力（任意。空欄は30として精度フラグを立てる）、コンディションの指定（顔グリッドでタップのたびに段階が巡回し、最後は「不明」に戻る）から `startRun` 操作を作り、履歴をそれ1件で置き換える。指定しなかったメギドは「不明」として扱い、`conditionsUnknown` が立つ間は帯に精度の警告を出す。今のランに記録がある場合は置き換えの警告を出す（月の締めを先に勧める）。
- 塔効果バフ: 探索の操作に `buffGains`（上がったステータスと%）と `buffPower`（虹の複合の塔破力+2）を載せ、導出でスタイルごとに蓄積する。蓄積の実量（`buffRaw`）は上限前で保持し、表示値（`buffs`）は HP・攻撃30%／防御50% で頭打ちにする（ダメージ上昇の上限は wiki に明記が無いため頭打ちにしない）。流れは箱色→（ステータス上昇マスは上がったステータスを確認）→上昇幅の候補（構造データの箱効果の表から生成）をタップして確定。確定後はシートを開いたまま蓄積と上限の警告を見せる。帯には蓄積がある間だけ1行で出す。バフの効果の反映は M3 の値打ち判定（拡張1）と M8 の確認表示で実施済み（下記「M3 値打ち判定と M8 バフ反映」）。
- メギド画面: 所持は負の選択。`megidoDetails` が未設定の間は全員所持として扱い、最初の切り替えで全員分を「所持あり」で具体化してから反転する（所持の意味論は第1スライスのまま）。育成は行の展開で入力する: レベル（70/75/77/79/80 の選択）、奥義Lv（数値入力 1〜99）、専用霊宝（あり／なし）、絆霊宝（なし／真／剛／絆）、凸（数値入力）。需要の件数は、手段の索引が未生成のため「未集計」と明示する枠のみ（偽の件数は出さない）。

## 移行の扱い

- 初回起動時、保存が空で移行記録が無い場合にだけ、旧 localStorage の `formations` と `megidoDetails` を読む（読み取りのみ。旧データは書き換えない）。
- 編成は辞書形式と旧・配列形式の両方を受け、5枠（リーダーは中央 index 2 の位置のまま）、オーブID、霊宝ID、leaderSkill を写す。表示用の非正規化フィールド（名前等）は落とし、表示時に基礎データから引く。
- 所持・育成は確定した7フィールド（owned／level／ougiLevel／special_reishou／bond_reishou／singularity_level／reishou）にデフォルト補完して写す。
- ラン進行中の状態は引き継がない。移行があった初回は、結果（編成の件数、所持数、読み取れなかったキー）をシート1枚で表示する。

## 第4スライス（M7 の組み替えと M6 の核）で決めた意味論

- 探索の組み替え（M7）: 提示された期待度3の組み合わせを初期表示とし、メンバーをタップすると候補ビュー（所持・気絶でない・編成にいない者、探索力の高い順）が開いて入れ替え・追加（最大3体）・除外ができる。入れ替えのたびに合計探索力と到達できる期待度を再計算して表示する。到達できる期待度が下がる組み替えも利用者の判断として許し、現在の期待度を正直に出す。結果の記録（箱色）には、最終的に確定した組み合わせが使われる。「提示された組み合わせに戻す」で答えに戻れる。需要回避は手段の索引（ME待ち）のため作らない。
- 編成を組む（M6・核）: M5 の一覧から新規作成・編集・削除ができる（削除は2段階の確認）。枠タップ→候補タップで組み、候補の既定の並びはコンディション順、検索とスタイル・クラスの絞り込みつき。他の枠のメンバーと同一キャラクターは候補に出さない。枠ごとのオーブ選択では、装備条件（スタイル）が合わないオーブは理由つきで選べない。メンバーを替えてオーブの装備条件が合わなくなった場合はオーブを外す。名前は自動名（リーダー名＋編成）を初期値として編集できる。中央（リーダー、index 2）が空の編成は保存できない（保存ボタン自体を押せなくし、理由は保存ボタンの直上に出す。2026-11-19 の表示修正で変更。末尾の「編成管理・編成作成の表示修正」参照）。新規保存後はマスのシートへ戻り、そのまま確認表示（M8）に入る。編集保存後は一覧へ戻る。
- M5 の空状態（原則8の適用）: 保存済み編成が0件のときは検索・絞り込みを前面に出さず、作る導線を画面の中心に大きく出す。1件以上ある通常状態では検索・絞り込みを前に置く。フィルタで0件になった場合は通常状態のまま「条件に合う編成がありません」と出す。（文言と並びは 2026-11-19 の表示修正で変更: 画面名「編成管理画面」、説明→状態の順、ボタン名「編成を作成」。末尾の「編成管理・編成作成の表示修正」参照。）
- 表示の原則（ui-flow 原則8）の適用: M7 では現在の組み合わせの合計と期待度を節の中で最も大きく出し、候補の細目は候補行の中に収める。M6 では編成の成立に関わる情報（リーダーの有無、保存できない理由）を前に出し、候補の細目は候補行の中に収める。ME 未収録の注記などの常設の参考情報は小さい注記のままにする。
- 未実施（ME データ待ち）: M6 の ME 適合表示（エディタには未収録の注記だけを置き、構造のみ用意）、対策での候補の絞り込み、M7 の需要回避、M5 のカバー表示、M8 の ME 要約。
- 探索の報酬表示（M7、2026-11-18 追記）: 箱色は探索した後に分かる結果であり、利用者が操作できるのは探索力の方。そのため先頭の報酬表示から箱色の規模表を外し、人員の節に「現在の組み合わせの期待度なら何が出る所か」を見込み（予測報酬）として出す。見込みは構造データの箱効果表から期待度（1→緑、2→青、3→赤か虹）で引いた導出のみで、表に無い規模は作らない（例: 回復5500の期待度1は見込みを出さない）。組み替えで期待度が動けば見込みも連動する。箱色の規模表は「箱色ごとの規模（参考）」として下位に置き、閲覧専用のシートでも同じ扱いにする。結果の記録は従来どおり箱色。ランダム回復マスでは、先頭にスタイル別の疲労の偏り（絶好調より悪い人数、気絶は内数）を添えて賭けの中身が読めるようにする。閲覧専用のシートには組み合わせが無いため、見込みは出さない（規模表の降格のみ同じ）。

## 第5スライス（表示の組み直し）で決めた意味論

- 見通し帯の階層化（原則8）: この階の回復と見通しの結論を前の大きい行にし、全スタイルの次の回復は圧縮した1行に落とす。変わらない事実の説明（最短路上に塔破力マスは無い等）は戦績が無い間だけ出し、戦闘・探索の記録が付いたら畳む（見通しの行は塔破力と次の塔破力マスだけになる）。気絶・絶不調の体数は判断に近いので残す。元に戻す・やり直しの知らせは帯の先頭に短く出す。
- 上部バーのメニュー化（原則3改訂）: 元に戻す・やり直しは上部バーから外し、右端のメニューボタンから開くメニューの中の文字の行にした（履歴が無い側は無効表示）。実行したら、何を取り消した（進めた）かを帯の下に短く知らせる。確認ダイアログは入れない。第3スライスまでの「上部バーに元に戻す・やり直し」は、この形に置き換わった。
- マップの階層化: 未解放のマスはラベルを小さく落とす。マス数の少ない階は、占有している行・列の範囲だけを描き（空の外周を切り詰め）、間隔を広げて下半分の空白を埋める。
- 未解放マスの案内（M2）: 未解放マスのシートは、事実より先に「解放するには、このマスを処理する」を出す。出すのは解放済みの隣接マス（あれば。それを処理すれば解放される）、無ければ未解放の隣接マスで、タップでそのマスのシートへ移れる。そのマスがボスへの道の途中か寄り道側かも添える（開始マスとボスからの最短路で判定する純粋関数 `unlockGuidance`）。事実（敵・ルール・コスト、探索の見込み等）はその後に置く。
- 記録画面の組み直し: 用件の順に並べる。今のランの戦績と過去のランの手渡しを先頭に大きく。出せるものの無い節（戦績不足の傾向、見つかっていないズレ、まだ無い過去のラン）は1行に縮める。月の締め・途中からの開始・書き出しと読み込みは最下部に「その他の操作」の行として引っ込める。ズレの疑いや傾向が実際に出せる時は、それらが節として前に出る。
- メギド画面の組み直し: スタイルごとに区切って所持体数を出し、スタイル単位の一括の所持切り替え（誤タップ防止のため2段階）と「未所持のみ表示」を付けた。行に出すのは所持の判断に要る情報だけにし、コンディション表示は外した（コンディション画面の仕事）。育成の入力は例外方式: 未所持のメギドには育成フォームを出さない。標準（レベル70・奥義Lv3・専用霊宝なし・絆霊宝なし・凸0）からズレている人を先に並べ、ズレの内容を行に出す。標準のままの人は「標準のまま ○体」と畳む（検索中と未所持のみ表示の間は畳まない）。複数選択しての一括設定（奥義Lv・レベル）も付けた。
- コンディション画面の組み直し: 既定の表示は、段階ごとの体数と、絶好調未満の人を悪い順に並べた一覧（誰もいなければ「全員絶好調」の1行）。全員の顔グリッドはズレの直しのための道具として開く形にした。次の回復の表示は残す。段階の直しは、顔や行をタップした瞬間に画面下部へ固定表示されるパネルで行う（対象の名前と段階のボタン。段階をタップしたら即反映してパネルを閉じる。グリッド内への差し込みはやめた）。タップした顔・行は選択中と分かる表示にする。
- 途中開始（H3）の指定方式: 画面の先頭に「指定しない人の扱い」を1回だけ選ばせる（絶好調として始める／不明のまま）宣言を既定値とし、個別に指定した人だけが例外になる形にした。段階の指定は巡回タップをやめ、コンディションの直しと共通の固定パネル方式に揃えた（段階または「不明」を1タップ）。名前での検索も付けた。`startRun` の意味論（不明の扱い、精度警告）は変えていない: 既定が「絶好調」なら未指定は既知（絶好調）として入り、「不明のまま」や個別の不明が残る場合は従来どおり `conditionsUnknown` が立つ。第3スライスの「タップで段階が巡回」はこの形に置き換わった。
- 編成へのアクセス: マップ下部の固定バーに「編成」を追加し、編成の一覧を管理モードで開けるようにした（戦闘の文脈なしに新規作成・編集・削除。0件なら空状態、1件以上でも新規作成の入口が常にある）。戦闘マスのシートからの「編成を選ぶ」は選択モードのまま。モードの違いは一覧側で吸収する（選択モードはタップで選んでシートに戻り、管理モードはタップで編集側に進む）。保存の戻り先も文脈で決める: 選択モードの一覧から作った新規だけが M8 の確認表示へ戻り、管理モードで作った場合は一覧へ戻る。
- 探索の結果付け（M7 確定形。色は一切選ばせない）: 期待度が決まれば標準の効果は固定なので、結果付けで入力するのは結果のブレだけにした。期待度1・2は質問なしで、下部バーの「探索した」1タップで確定する。期待度3は「探索した」（標準の効果で確定）と「上振れした」を並べ、上振れの入力は色の名前（赤／虹）を出さず効果側の言葉で聞く。虹の回復で規模が2通りある階層（30体×1段階／20体×2段階）でのみ、上振れの規模も同じ場面で選ばせる。それ以外の上振れでは追加の質問は無い。記録は効果で持ち、内部表現として箱色のキー（と規模の `recoveryVariant`）は残すが、色を選ばせる UI はどの画面にも置かない（結果の付け直しも効果の選択肢で聞く。履歴や手渡しの表示も「標準の効果／上振れ」で表す）。バフマスの能力・量の確認、ランダム回復のスタイル確認は従来どおり。タップ数: 結果付けは期待度1・2で1タップ、期待度3でも標準なら1タップ、上振れの入力が増えても2タップまで。第4スライスまでの「結果は箱色で記録し、4色ボタンで選ぶ」形は、この形に置き換わった。
- オーブの装備判定（旧データの意味論の確定）: 装備条件は「使用できるスタイルの条件」であり、種族は装備可否に入らない（種族はオーブ自体の種族であり、種族特効の対象。旧ツールの判定もスタイルのみだった）。具体ケース: カウンターのメンバーに対して、つちのこ（カウンター／爬虫類）も、とらまる（カウンター／物体）も装備できる。実際に間違っていた判定は専用オーブ（装備条件がメギド名のもの）で、従来は誰も装備できなかった。表記は3通り（そのままの名前／スタイル付きの名前「ウェパルB」／「名前（スタイル）」）あり、`orbEquippableBy` で判定する。オーブ選択の一覧には、そのメンバーに装備できるものだけを出し（付けられないものを並べること自体がノイズになるという判断）、検索もその範囲で効かせ、件数は「装備できるもの ○件」で出す。第4スライスの「理由つきで選べない」形は、この形に置き換わった。
- 検索の IME 対応と正規化: 検索欄のある全ビュー（編成一覧、メギド一覧、編成の候補、オーブ、途中開始）で、変換中（composition 中）は再描画で入力欄を作り直さない配線（`bindSearchInput`）にした。変換が確定してから絞り込みが走る。照合は、クエリと対象の両方を正規化（NFKC で全角・半角を吸収し、ひらがなをカタカナにそろえる `normalizeSearchText`）してから行う。
- 破壊的な操作の重さづけ（原則9）: 読み込み（全体の上書き）は、実行前に上書きされる内容と元に戻せないことを示し、先に書き出しで退避する案内を出した上で、画面に表示された4桁の数字（表示のたびに変わる）を正しく入力しないと実行できない形にした。編成の削除は、その場の2タップ確定をやめ、一覧のボタンとは別の場所（確認のシート）に編成名を明示した確定ボタン（『○○』を削除する）を置いた。月の締めは、残るもの（過去のランとして保存される記録）とリセットされるもの（コンディション・塔破力・解放状態）を示す確認を挟む。元に戻せる操作（結果の付け直し、コンディションの直し等）は対象外で軽いまま。第4スライスの「削除は2段階の確認」は、この形に置き換わった。
- 階一覧: クリア済み（ボス勝利済み）の階に「済」の印を付けた。
- 未実施（ME データ待ち）は従来どおり: ME 適合表示、対策での候補の絞り込み、需要回避、M5 のカバー表示、M8 の ME 要約には触っていない。

**切り分けは2層**（2026-11-18 の較正・最終版、マスター: 「完全にゲーム画面だと、操作中のノイズになる部分もあります。ツールはツールだと認識しつつ、『カウンターってこんな感じの色だよね』って部分とかにストレスを入れたくないんです」）:

1. **認識のアンカー（意味を持つ色）= ゲームの色感に合わせる。ここは譲らない。** スタイル色、コンディション段階の色、マスの種類の色、期待度の色など、「それが何か」を色で認識する部分。現行ツールのルールは、ゲームに寄せて作られた記録として参照する（棚卸し: `research/current-tool-performance-teardown.md` §7.1）。

## マップ描画の幾何バグ修正（2026-11-19）

- 症状: 1F以外でマップ全体がずれ、マスが右端からはみ出し、接続線がマスの中心に合わなかった（ユーザー目視、20F/23F）。

## 広い階のマス寸法の固定化（2026-11-19）

機能側の便の申し送り（7列以上の階でマス幅が68pxから圧縮される）への対応。ui-flow 追記12の決定「マス寸法は固定、収まりは地図側で吸収」を全階で実現した。

### 吸収の方法と理由

- 列トラックを `minmax(0, 74px)` から全階固定の `74px` に変えた（マスは margin 3px を引いた 68×50 で全階不変）。行は従来どおり 56px 固定。
- 地図側の吸収は横スクロール: ステージ（`.map-stage`）をグリッドの自然寸（列数×74px、`width: max-content`）に固定し、その外側に `.map-scroll`（`overflow-x: auto`）を置いた。列の少ない階はステージが領域より細く、margin の自動配分で中央に寄る（従来の見え方を維持）。列の多い階（7列=518px、9列=666px）は領域内で横スクロールし、ページ全体は横にはみ出さない。
- 初期のスクロール位置は renderMap が決める: 開始マスと次に処理できるマスの中点が領域の中央に来る位置（片方しか無い閲覧中の階は開始マスを中央）。同じ階の再描画では利用者が動かした位置を復元し、その位置で次のマスが見切れる場合だけ見える所まで寄せる。階が変われば初期位置に戻る。
- 横スクロールを選んだ理由: マス寸法を固定したまま全マスへ到達できる吸収は、スクロールか縮小しかない。縮小は決定（追記12）が禁じた伸縮そのもの。開始マスは広い階でも中央列（7列は3列目、9列は4列目）にあり、初期位置の決め方と合わせて、開いた直後に開始と次が見える。

## チェイン道具の作り替え（2026-11-19、ユーザー承認済みの新方式）

ユーザーとの擦り合わせ（見た目の予想モックで承認）で、経路チェッカーを方式ごと置き換えた。道具の目的は「敵の行動を割り込めるのか」を試すこと。区画の見出しは「チェインのテスト」で、編成エディタの「編成を組む」の下に出す（チェインに関わるメンバーがいる編成でのみ。従来どおり）。

### 方式

- **タイムテーブル**: 編成の味方とターゲットの敵（対象マスの敵全員）を実効素早さ（speed.js）の順に横一列に並べ、素早さの数値を出す。敵は対象マスの実構成（floor データのパーティ）からで、素早さはそのデータの値。ターゲットが選ばれていない場合は味方だけが並ぶ。
- **起点**: 味方チップのタップで起点にする。起点はタイムテーブルに残り（金色＋「起点」の印）、その直後に ∧ の印（「ここに割り込む」）を出して、チェインテーブルがタイムテーブルのどこに割り込むかを示す。起点にできるのは基本は始動の形か回数チェイン付与を持つ者。できない者をタップすると「○○は起点にできません（理由）。」の行で理由を出す（チェインを持っていない／チェイン中しか繋げない（始動にはならない）／自身へのチェインしかない／専用霊宝が付いていない）。
- **自動で引っ張る**: 起点の後、実効素早さの順に次の味方をチェインテーブル（下段の別の表）へ移し、その味方がチェインを渡せる限り繰り返す。渡し方は形の候補から条件の軽いものを選ぶ（調整フライトの「重さ」の計算をそのまま使う。専用霊宝の付いていない形は候補から外す）。渡せなければ回数チェイン付与（本人の付与→編成の付与持ちの存在）で繋ぐ。形はあるが専用霊宝の付いていない形しか残っていない場合は、その理由で止まる。
- **行動の列とフォトンの上限**: チェインテーブルはメンバーではなく行動の列。同じ味方も2回目まで並び（「2回目」の印）、行動の総数はフォトン5個（起点の分を含む）で止まる。フォトンを使い切った時はその旨を出す。
- **外す操作**: チェインテーブルの行動をタップすると、その行動を「フォトンを乗せなかった」扱いにして最初から組み直し、空いた分に次の候補が入る。起点（1つ目の行動）をタップするとテスト全体を消す。リセットのボタンでも消せる。
- **対象の縛り（例外・固定）**: 始動・中継の形に対象の縛り（最も攻撃力が高い味方／最も素早さが低い味方）がある場合、その形で渡す相手は素早さ順ではなく条件の相手（自分を除く編成内で最大／最小。同点は編成順）になり、◎ の印と破線で「条件で固定」と示す。固定の行動はタップしても変わらない。
- **回数チェイン付与（例外）**: 編成に味方・全体への回数チェイン付与の持ち主がいる場合、チェインを持たない味方も起点・中継になれる（ユーザー裁定: 判定は編成に付与持ちがいるかだけ。自分への付与だけの者は編成の例外には数えないが、本人の受け渡しには使える）。その場合は区画にその旨の注記を出す。
- **結果の文**: チェインが組み上がると、「割り込み成立: ○○ → … の順に、敵の○○（素早さN）より先に N 回の行動が入ります」の形で、起点より後ろの最初の敵を名指しで出す。起点より後ろに敵がいない場合は、起点より前の最後の敵より遅いことを出す。フォトンの使い方（何個使うか、起点の他に積む分があるか）も併記する。

### 引き継いだ材料と、引き継がなかったもの

- 引き継いだ: 能力の検出データ（data/chain.v1.json）、専用霊宝の条件判定、フォトン供給の3段の注記と形の優先付け（調整フライト。供給の材料表示はタイムテーブルの味方チップに添える）、回数チェイン付与の受け渡し、対象の縛りの判定。
- 引き継がなかった（新方式では役割が変わったため）: 旧チェッカーのつなぎ目ごとの判定文（届く／条件が足りない／速さが合わない）と、経路の中に差し込む敵の割り込みチップ。割り込みの可否はタイムテーブル（起点と ∧ の位置）と結果の文が担い、速さの並びは自動で引っ張る規則そのものになった。

- 公式の要素で組む: 付与者Lv（基準70）・倍率・素材ボム数（錬成回数+解除した速・重の総数、上限30）・同時爆破補正=1+0.1×同時個数・ダメージ上昇状態はボム単位で錬成に引き継ぐ（値は最大を継承。オロチ特性の重+20%は本人の重だけに乗り、錬成では落ちる）。
- 素材ボム数の効きは公式式が無いためWiki由来の式（錬成補正=(錬成回数+解除した速・重の総数)×付与者Lv×2.5）を採用。検証ケース（Lv70・素材16・倍率50・同時1.2・防御9999→225,001）が外部計算ツールと一致することを単体テストで固定。
- 範囲: 単体=1体、横一列=対象と同じ列（クラスで決まる前列／後列）の全員（3体いれば3体）、全体=全員。3個上限と同能力1個までの判定は付いた先の敵ごと。速の巻き込みはスロット順で左右に最も近い敵（空きマスは飛ばし、列は無関係。誘爆の連鎖も同じ届き方）、錬の波及は対象以外へ半分。範囲はコーパスの能力原文から引く（リヴァイアサンのスキルは滞水だけが広がる話で、錬成自体は原文どおり単体で範囲化の対象外）。錬成は対象に何が付いているかで可否が変わらない（速だけでも素材になる。何も付いていなくても錬成でき、倍率は錬成能力の倍率だけになる）。

### 霊宝のダメージ上昇への対応（2026-11-19 夜、修正フライトの追加作業）

- 対象は特性「ハイドロボムのダメージが○%上昇する」を持つ霊宝2件のみ: 修羅の仮面+3%（水心10）と慈愛と安寧の香炉+4%（水心20）、どちらもレイガンベレット系。命中率と付与時回復の霊宝は対象外。生成器（generate-hbomb.mjs）がコーパス霊宝から拾い、索引に reishouBoost（霊宝ID→上昇率）として持つ。
- 装備はメギド側の装備スナップショット（megidoDetails の reishou、最大4個）から読む。装備分はそのキャラの装備合計（同じ霊宝の重複も個数分を合計）。
- 演算（ユーザー決定で確定）: 上昇値 = 状態系の値（錬成では素材の最大値を継承）+ 付与者（錬では錬成者）の装備分。装備分はボム1個につき1度だけ付き、素材経由・錬成回数では増えない（錬成のたびに錬成者本人の装備合計で付け直す）。例: 専用霊宝つきヒュトギン奥義の強化+70%に修羅の仮面+3%で合計73%。仮面持ちが何回錬成しても73%のまま。区画には装備者の注記（「霊宝: ○○のハイドロボムのダメージ+○%」）を出す。
- あわせて配線の不備を修正: 氷龍帝オロチ（オーブ）の特性「ハイドロボム重のダメージ+20%」は、索引と selfBoost の仕組みはあったが、オーブ自身の行動にしか紐付いておらず、実際に置く重へ乗っていなかった。装備者の全行動へ紐付けるよう直し、本人の重に乗ることと錬成で失われることをテストで固定した（ユーザーの理解どおり、錬は「付与したボム」とは別物になる）。
- 検証: 単体テスト合格2,368件・失敗0件（霊宝の演算・73%の例・重複装備・オロチの乗りと消失を含む）、パイプライン検証29/0、プレビュー検証17/17、実ブラウザ11/11（列3体・速の飛ばし届き・ゴウギ戦のおまかせ）。SW の APP_VERSION は 31 に上げた。

## 横断検索への効果文の追加（2026-11-20、SW83）

ユーザーの指示: 候補の計算に載っていない機構（無敵・根性・回避・
レイズギフト・弾撃など）も検索できるといい。従来の横断検索は
マス（敵名・ルール）・メギド名・編成だけが対象で、効果文は探せず、
オーブは名前でも対象外だった（「ケイブキーパー」「無敵」とも0件）。

- 索引: 生成器 pipeline/generate-search-index.mjs が、生成済み
  データ（abilities 272件・orbs・me）から search-index.v1.json
  （952,482 バイト）を作る。内訳は能力3,069件（特性・スキル・
  覚醒スキル・奥義・秘奥義の名前と文面）／オーブ606件（名前・
  特性・スキル）／ME 1,378件（同じ効果文は枠をまとめて重複排除）。
  起動時の読み込みには含めず、検索ビューを開く時にだけ遅延読込
  する（初回読み込みのデータ増分はゼロ。SW の /data/ 実行時
  キャッシュで再訪時はキャッシュから読む）。
- 照合: js/search.js（純関数）。正規化は既存検索と同じ
  normalizeSearchText。正規化済みの影は読み込み時に1回だけ作り、
  キー入力ごとの再正規化を避ける（実測: 索引読込＋最初の結果
  表示まで約260ms、読込後の入力→結果表示は約18ms）。
- 結果の形: 群は マス → メギド → 能力 → オーブ → マスエフェクト
  → 編成。行は main が「誰が・どの形で」（例: ユフィールC 奥義
  「ゼーレグナーデ」／ケイブキーパー スキル／リリス マスエフェ
  クト（枠1・枠2・リーダー枠））、sub がヒットした語の前後の短い
  抜粋。ピッカーの密な行は流用しない。各群の上限は20行（既存の
  メギド・編成と同じ）。能力の＋／＋＋／Lv違いは基本形の名前に
  畳み、最初に当たった形の文面から抜粋を取る（行の氾濫防止）。
  オーブは名前が当たれば名前の行だけ（詳細で全文が読める）。
- 飛び先: 能力・ME の行は既存のメギド行と同じくメギド画面へ
  （そのメギドで絞り込み）。オーブ単体の詳細画面はアプリに無く、
  オーブピッカーは編成の文脈が無いと開けないため、検索から開く
  最小のオーブ詳細シート（buildOrbDetailSheet: 名前・メタ・
  特性文・スキル文）を新設した。openSheet が検索の全面ビューを
  閉じて文脈が落ちるため、文脈を控えて復元し、バーのボタンと
  シート外タップも onCloseRequest で同じ復元に振り分ける。
- 語の実在は生成データで確認した: 「根性」はマルチネCの奥義名
  「純然たる根性の原動」とオーブ「スケアス」のスキル文にだけ

  能力名も照合対象に含めたのはこのため。「回避」もアザゼルの
